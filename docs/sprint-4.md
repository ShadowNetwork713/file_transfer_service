# Спринт 4 — запуск двух нод и обмен блоками

> Практическая инструкция для воспроизведения сетевого сценария из двух узлов. Команды рассчитаны на Windows CMD.

В спринте 4 добавлена демонстрационная HTTP-сеть из независимых экземпляров блокчейна. Ноды **A** и **B** используют разные каталоги данных и общаются по HTTP. Для запуска достаточно Python 3.12+; дополнительных библиотек для работы сервера не требуется.

Ниже команды для **Windows CMD** (обычная командная строка Windows). Выполняйте их **из корня репозитория**, где находятся `app/` и `pyproject.toml`. Используются три окна CMD: отдельно для каждой ноды и ещё одно — для запросов. Порты 8765 и 8766 должны быть свободны.

## 1. Подготовка проекта

Для нового клона:

```bat
git clone https://github.com/ShadowNetwork713/file_transfer_service.git
cd file_transfer_service
git fetch origin
git switch develop
```

Если репозиторий уже скачан и рабочее дерево чистое:

```bat
git switch develop
git pull origin develop
```

> Если работа ведётся в другой ветке, используйте её вместо `develop`, **но убедитесь, что в ней присутствуют** `app/network/server.py`, `app/network/node.py`, `app/network/instance.py`, `app/network/contracts.py`, `app/network/client.py` и `Blockchain.append_external_block` из `app/core/blockchain.py`.

## 2. Запуск ноды A (первое окно CMD)

```bat
python -m app.network.server --node-id A --data-dir data/node-a --port 8765 --demo
```

Ожидаются строки вида:

```text
Node A: http://127.0.0.1:8765  data=...
UI: http://127.0.0.1:8765/
```

Оставьте окно работающим. Аргумент `--demo` включает эндпоинт создания тестового блока (`POST /api/v1/demo/blocks`).

## 3. Запуск ноды B (второе окно CMD)

```bat
python -m app.network.server --node-id B --data-dir data/node-b --port 8766 --demo
```

Ожидаются строки вида:

```text
Node B: http://127.0.0.1:8766  data=...
UI: http://127.0.0.1:8766/
```

Каждая нода хранит свою цепочку отдельно:

```text
data/
  node-a/
    chain.json
    .node.lock
  node-b/
    chain.json
    .node.lock
```

`chain.json` сохраняется на диск, поэтому после штатного перезапуска ноды история сохраняется. Файл `.node.lock` защищает один каталог данных от одновременного использования несколькими процессами. **Не запускайте A и B с одним `--data-dir`.**

## 4. Проверка начального состояния (третье окно CMD)

```bat
curl.exe -s http://127.0.0.1:8765/api/v1/status
curl.exe -s http://127.0.0.1:8766/api/v1/status
```

На свежих каталогах обе ноды находятся на высоте `0`: существует только genesis-блок. Пример ответа A:

```json
{
  "networkId": "demo-v1",
  "protocolVersion": 1,
  "nodeId": "A",
  "height": 0,
  "tipHash": "1c9a8033388f13fa939256e0aa874d636e0ba2ffe64077a2823ddc74d5bcefd5",
  "genesisHash": "1c9a8033388f13fa939256e0aa874d636e0ba2ffe64077a2823ddc74d5bcefd5",
  "chainValid": true
}
```

У ноды B будет такой же ответ, но `"nodeId": "B"`. Общие `networkId`, `protocolVersion` и `genesisHash` — условия совместимости пиров.

## 5. Создание блока на ноде A

```bat
curl.exe -i -X POST http://127.0.0.1:8765/api/v1/demo/blocks -H "Content-Type: application/json" -d "{}"
```

Ожидаемый HTTP-статус: **201 Created**. Пример реально полученного ответа (хеши и идентификаторы в следующем запуске будут другими):

```json
{
  "status": "CONFIRMED",
  "txId": "ed780e1e484d47dd21541b66a64ab2a65478b403a867d177fdddfcf4f0f17780",
  "blockIndex": 1,
  "blockHash": "a372d12c7c4c97a47fba6c6ccce1455e0ca237722d1fd6c66caf94ac6ba7effa"
}
```

`CONFIRMED` означает, что запись документа добавлена в новый **локальный** блок A. После запроса высота A станет `1`, а высота B пока останется `0`: **автоматической рассылки созданных блоков нет**.

## 6. Передача блока от A к B через pull

Запрос отправляется **на B**, которая должна забрать следующий блок у A. Адрес `peerUrl` — это базовый URL **источника**, а не самой B:

```bat
curl.exe -i -X POST http://127.0.0.1:8766/api/v1/peers/pull -H "Content-Type: application/json" -d "{\"peerUrl\":\"http://127.0.0.1:8765\"}"
```

Ожидаемый HTTP-статус: **200 OK**. Пример ответа:

```json
{
  "status": "ACCEPTED",
  "code": "OK",
  "message": "Блок принят и сохранён",
  "blockIndex": 1,
  "blockHash": "a372d12c7c4c97a47fba6c6ccce1455e0ca237722d1fd6c66caf94ac6ba7effa"
}
```

B запрашивает у A статус и блок `1`, проверяет структуру, номер, связь `prevHash`, хеш блока и хеши записей, после чего добавляет блок в свой `chain.json`.

Проверьте обе ноды:

```bat
curl.exe -s http://127.0.0.1:8765/api/v1/status
curl.exe -s http://127.0.0.1:8766/api/v1/status
```

Критерии успеха: **`height` равен `1` у обеих нод; `tipHash` одинаковый; `chainValid` равен `true`.**

Если повторить такой же `pull`, ожидается **200 OK** и ответ:

```json
{
  "status": "ALREADY_SYNCED",
  "code": "OK",
  "message": "Вершины цепочек уже совпадают"
}
```

## 7. Альтернативный обмен: push и announce

**Push:** создайте ещё один блок на A, затем отправьте следующий недостающий блок на B:

```bat
curl.exe -i -X POST http://127.0.0.1:8765/api/v1/demo/blocks -H "Content-Type: application/json" -d "{}"
curl.exe -i -X POST http://127.0.0.1:8765/api/v1/peers/push -H "Content-Type: application/json" -d "{\"peerUrl\":\"http://127.0.0.1:8766\"}"
```

Здесь запрос идёт **на A**, а `peerUrl` — адрес **получателя B**. При успехе будет **200 OK** и `"status": "ACCEPTED"` с `"blockIndex": 2`. Снова сравните высоты и `tipHash` двух нод.

**Announce (оповещение о новом блоке):** на синхронизированных нодах создайте очередной блок A и уведомите B:

```bat
curl.exe -i -X POST http://127.0.0.1:8765/api/v1/demo/blocks -H "Content-Type: application/json" -d "{}"
curl.exe -i -X POST http://127.0.0.1:8765/api/v1/peers/announce -H "Content-Type: application/json" -d "{\"peerUrl\":\"http://127.0.0.1:8766\"}"
```

A отправляет B номер и хеш своего последнего блока и адрес источника. B **сама скачивает** объявленный блок у A и валидирует его. Ответ успешного оповещения — **200 OK**, `"status": "ACCEPTED"`; повторное оповещение о том же блоке возвращает `"status": "ALREADY_PRESENT"`.

**Все три операции (`pull`, `push`, `announce`) выполняются вручную и передают не более одного очередного блока за запрос.** Если A опережает B на несколько блоков, повторите команду, пока высоты и вершины не совпадут. `announce` сообщает только о **последнем** блоке, поэтому если у B отсутствуют предыдущие блоки, сначала догоните цепочку через `pull` или `push`.

## 8. Пример отклонения блока: конфликт цепочек

Этот сценарий запускается **после шагов 1–7**, когда цепочки A и B синхронизированы.

1. Создайте по одному **разному** демоблоку на A и на B, **не синхронизируя** их между собой:

   ```bat
   curl.exe -i -X POST http://127.0.0.1:8765/api/v1/demo/blocks -H "Content-Type: application/json" -d "{}"
   curl.exe -i -X POST http://127.0.0.1:8766/api/v1/demo/blocks -H "Content-Type: application/json" -d "{}"
   ```

2. Попробуйте отправить блок с A на B:

   ```bat
   curl.exe -i -X POST http://127.0.0.1:8765/api/v1/peers/push -H "Content-Type: application/json" -d "{\"peerUrl\":\"http://127.0.0.1:8766\"}"
   ```

Ожидаемый HTTP-статус: **409 Conflict**. Реальный пример ответа:

```json
{
  "status": "REJECTED",
  "code": "BLOCK_CONFLICT",
  "message": "Разные вершины на одной высоте"
}
```

Обе цепочки достигли одной высоты, но последние хеши различаются. Нода **не заменяет** свой блок чужим и не выполняет автоматическое разрешение форка.

Чтобы увидеть отказ **непосредственно при приёме блока** (`POST /api/v1/blocks`), получите конфликтующий блок A и направьте его в B (в приведённом примере это блок `4`, если вы выполнили все шаги последовательно):

```bat
curl.exe -s http://127.0.0.1:8765/api/v1/blocks/4 > block4.json
curl.exe -i -X POST http://127.0.0.1:8766/api/v1/blocks -H "Content-Type: application/json" --data-binary "@block4.json"
```

Ответ **409 Conflict** содержит `"status": "REJECTED"`, `"code": "BLOCK_CONFLICT"`, `"blockIndex": 4` и `"blockHash"` отклонённого блока. Фактическое сообщение имеет вид `"Блок 4 расходится с локальной цепочкой"`. Номер `4` верен только для указанной последовательности (первый блок через `pull`, второй через `push`, третий через `announce`, четвёртый создан отдельно на каждой ноде).

## 9. Запуск сценария через веб-интерфейс

Откройте в браузере два адреса:

- [Нода A — http://127.0.0.1:8765/](http://127.0.0.1:8765/)
- [Нода B — http://127.0.0.1:8766/](http://127.0.0.1:8766/)

На странице A нажмите **«Создать блок»**. На странице B укажите пир `http://127.0.0.1:8765` (при указанных портах адрес подставляется автоматически), нажмите **«Запросить состояние»**, затем **«Забрать блок»**. После обновления статусов сравните высоты и хеши вершин: интерфейс должен показать **«Истории совпадают»**. Кнопка **«Отправить блок»** запускает `push` от текущей ноды к указанному пиру. Веб-интерфейс не содержит отдельной кнопки для `announce`: для него используйте API выше.

## 10. Что реализовано и какие есть ограничения

| Возможность | Поведение в спринте 4 |
|---|---|
| Независимое хранение | Каждая нода сохраняет свои блоки в отдельный `chain.json` |
| Проверка целостности | Перед добавлением внешнего блока проверяются структура, индекс, `prevHash`, хеш блока и хеши записей |
| Совместимость | `networkId` (по умолчанию `demo-v1`), `protocolVersion` (`1`) и общий genesis должны совпадать |
| Обмен | Ручные `pull`, `push`, `announce`; **по одному блоку** за вызов |
| Повторная синхронизация | `ALREADY_SYNCED`, если высота и вершины совпадают; `ALREADY_PRESENT`, если тот же блок уже принят |
| Конфликт | Отклоняется с `REJECTED` / `BLOCK_CONFLICT`; автоматической перестройки цепочки, консенсуса и разрешения форков нет |
| Обнаружение других узлов | Адрес пира вводится вручную; автоматического поиска пиров нет |
| Сетевые адреса | По умолчанию разрешены только `localhost` и loopback-IP (например, `127.0.0.1`) |
| Удалённая сеть | Есть `--allow-remote-peers` и `--advertise-url`, но это **демо**, не защищённый публичный сервис |
| Защита HTTP | Нет HTTPS, аутентификации и авторизации для публичного сетевого API; **не выставляйте ноду в интернет** |
| Содержимое файлов | По сети пересылаются блоки с **метаданными и хешами** документов; сами PDF/DOCX и другие файлы не передаются |
| Деморежим | `POST /api/v1/demo/blocks` доступен только с флагом `--demo` |
| Ограничения протокола | JSON-запрос или ответ до 256 КиБ, не более 100 записей в блоке; таймаут обращений к пирам по умолчанию 2 секунды |

## 11. Ошибки и диагностика

| Симптом | Возможная причина / решение |
|---|---|
| `ModuleNotFoundError: No module named 'app'` | Откройте CMD в **корне репозитория** и запускайте через `python -m ...` |
| `Connection refused` / `PEER_UNAVAILABLE` | Проверьте, что обе ноды запущены и порты 8765/8766 соответствуют адресам |
| `PEER_TIMEOUT` (HTTP 504) | Пир не ответил вовремя; проверьте его доступность |
| `PEER_ADDRESS_FORBIDDEN` (HTTP 400) | Указан не-loopback адрес, а удалённые пиры по умолчанию запрещены |
| `PEER_INCOMPATIBLE` (HTTP 502) | Не совпадают `networkId`, версия протокола или genesis |
| `REJECTED` / `BLOCK_CONFLICT` (HTTP 409) | Две расходящиеся цепочки; автоматического слияния нет |
| `NOT_FOUND` (HTTP 404) для `/api/v1/demo/blocks` | Нода запущена без `--demo` (для POST на этот маршрут) |
| `Каталог данных уже используется другой нодой` | Используйте другой `--data-dir` или остановите процесс, который занимает каталог |
| `Address already in use` / ошибка привязки порта | Освободите порт или запустите ноду на другом свободном порту; обновите адреса в командах |

Ноды останавливаются сочетанием **Ctrl+C** в соответствующих окнах CMD. Для повторного запуска используйте те же команды: данные в `data/node-a/chain.json` и `data/node-b/chain.json` сохранятся. Если нужен **повтор сценария с чистого genesis**, сначала остановите оба процесса, затем удалите **только демокаталоги** `data/node-a` и `data/node-b` (это безвозвратно удалит их локальную историю):

```bat
rmdir /s /q data\node-a
rmdir /s /q data\node-b
```

После этого повторите шаги 2–8.

**Критерий завершения спринта:** новый участник команды без дополнительных пояснений запускает две ноды, создаёт блок на A, передаёт его на B, видит одинаковые `height` и `tipHash` при `chainValid: true`, воспроизводит конфликт `BLOCK_CONFLICT` и понимает ограничения демоверсии.
