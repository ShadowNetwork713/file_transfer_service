# Критерии приёмки ядра и глоссарий

## Критерии приёмки

Критерий считается выполненным, когда его проверяет хотя бы один автоматический тест (`tests/`) или тест-кейс из `07-test-cases.md`.

### Record (SER-35)

1. Одинаковые `recordId`, `documentId`, `fileHash` и `timestamp` дают одинаковый `recordHash`.
2. Изменение любого из этих полей меняет `recordHash`, и `Verify` возвращает false.
3. `recordHash` это hex в нижнем регистре длиной 64, считается BLAKE2b-256 от канонического JSON (ключи по алфавиту, без пробелов) без самого `recordHash`.
4. В записи нет имени файла и персональных данных: только `recordId`, `documentId`, `fileHash`, `timestamp`, `recordHash`.
5. Идентификаторы не в формате UUID и хеш не в формате hex 64 отклоняются с `ValueError`.

### Block (SER-36)

1. Хеш блока пересчитывается и совпадает с сохранённым.
2. Хеш считается по каноническому JSON заголовка: `index`, `timestamp`, `prevHash`, `recordHashes` (хеши записей по порядку).
3. Изменение `index`, `timestamp`, `prevHash`, состава или порядка записей меняет хеш блока.
4. Подмена содержимого записи внутри блока обнаруживается методом `Verify`.
5. Блок без записей допустим (genesis).

### Blockchain (SER-37)

1. Новая цепочка состоит из genesis: `index` 0, `timestamp` 0, `prevHash` из 64 нулей, записей нет. Хеш genesis одинаков при каждом запуске.
2. `AddBlock` присваивает следующий `index`, ставит `prevHash` равным хешу последнего блока и сам считает хеш. Блок без записей добавить нельзя.
3. `ValidateChain` возвращает true на целой цепочке.
4. `ValidateChain` возвращает false при подмене записи, блока, `prevHash`, `index`, порядка блоков, при удалении блока из середины и при подмене genesis.
5. В повреждённую цепочку блоки не добавляются (`InvalidChainError`).

### Хранение в JSON (SER-38)

1. Если файла `chain.json` нет, создаётся и сохраняется genesis.
2. После перезапуска цепочка поднимается из файла, валидна и продолжается новыми блоками.
3. Запись идёт через временный файл с подменой: при сбое прежний файл не портится, временных файлов не остаётся.
4. Если файл правили вручную или цепочка не проходит проверку, добавление блоков блокируется, ошибка уходит в лог.
5. Если файл нечитаем, добавление блоков блокируется, файл не перезаписывается.

### IBlockchainService (SER-39)

1. `RegisterDocument(documentId, fileHash)` помещает запись в новый блок и возвращает `CONFIRMED`, номер блока и `txId`, равный `recordHash`.
2. Повторная регистрация того же документа с тем же хешем возвращает прежний результат и не создаёт блок.
3. При повреждённой цепочке или ошибке записи на диск возвращается `FAILED`, цепочка не меняется, регистрацию можно повторить.
4. Некорректные `documentId` и `fileHash` дают `ValueError`, а не `FAILED`.
5. Document Module работает только через интерфейс и не знает про классы `Block` и `Record`.

## Глоссарий

| Термин | Значение |
|---|---|
| Запись (Record) | единица, которую регистрируем в блокчейне: идентификаторы документа и записи, хеш файла, время и хеш самой записи. Аналог транзакции |
| Блок (Block) | набор записей с номером, временем, ссылкой на предыдущий блок и собственным хешем |
| Цепочка (Blockchain) | последовательность блоков, где каждый блок ссылается на хеш предыдущего |
| Genesis | первый блок цепочки. Создаётся вручную с фиксированными полями, поэтому всегда одинаковый |
| Хеш | отпечаток данных фиксированной длины. В проекте BLAKE2b-256, hex в нижнем регистре, 64 символа |
| Канонический JSON | JSON с отсортированными ключами и без пробелов. Нужен, чтобы одинаковые данные всегда давали одинаковый хеш |
| `prevHash` | хеш предыдущего блока, который записан в текущем. Именно он связывает блоки в цепочку |
| `recordHash` | хеш записи. Он же `txId` и `transaction_hash` документа |
| Подтверждение (CONFIRMED) | запись попала в блок, блок сохранён, цепочка прошла проверку |
| FAILED | регистрация не удалась (цепочка повреждена или ошибка записи на диск). Документ не теряется, регистрацию можно повторить |
| PENDING | запись принята, но ещё не в блоке. В MVP не возвращается, оставлен на будущее |
| Валидация цепочки | проверка, что genesis на месте, номера блоков идут подряд, хеши блоков и записей пересчитываются, а `prevHash` совпадает с хешем предыдущего блока |
| `chain.json` | файл, в котором цепочка хранится на диске |
| Блокировка цепочки | режим, когда цепочка не прошла проверку или файл нечитаем: блоки не добавляются, пишется ошибка в лог |
| Proof (доказательство) | в MVP не реализовано. Планируется как поиск записи по хешу файла (`GetProof`) в следующем спринте |
