# 2. Основные компоненты

## Frontend

Frontend представляет собой веб-приложение, через которое пользователь взаимодействует с системой.

Frontend отвечает только за интерфейс и отправку запросов Backend API.

Основные страницы:

* регистрация;
* авторизация;
* мои документы;
* входящие документы;
* отправленные документы;
* загрузка документа;
* страница документа;
* проверка документа;
* история документа.

Frontend **не должен напрямую обращаться к базе данных, файловому хранилищу или blockchain**.

Всё взаимодействие выполняется через Backend API.

---

# 3. Backend API

Backend — основной компонент системы.

Он содержит бизнес-логику и связывает:

```text
Frontend
   ↓
Backend
   ↓
────────────────────────────────
↓           ↓          ↓
Database   Storage   Blockchain
```

Backend можно реализовать одним приложением, внутри которого будут находиться отдельные модули.

Для первой версии системы это предпочтительнее микросервисной архитектуры.

---

# 4. Auth Module

Отвечает за пользователей и авторизацию.

Основные функции:

```text
POST /auth/register
POST /auth/login
GET  /users/me
```

Модуль выполняет:

* регистрацию;
* проверку email;
* хеширование пароля;
* авторизацию;
* выдачу токена;
* проверку пользователя при запросах.

Пароль хранится не в открытом виде, а в виде безопасного хеша.

---

# 5. Document Module

Это центральный модуль работы с документами.

Отвечает за:

* загрузку;
* получение;
* скачивание;
* удаление;
* поиск;
* получение списка документов;
* хранение metadata документа.

Пример:

```text
POST   /documents
GET    /documents
GET    /documents/{id}
GET    /documents/{id}/download
DELETE /documents/{id}
```

Сам файл в базе данных не хранится.

В базе находится только информация:

```text
Document
--------------------------
id
owner_id
filename
size
storage_key
hash_blake2b
status
blockchain_status
transaction_hash
created_at
```

А содержимое файла находится в File Storage.

---

# 6. File Storage

Файловое хранилище отвечает непосредственно за хранение загруженных файлов.

Например:

```text
/files/
   ├── a81c.../
   │      └── contract.pdf
   │
   ├── 91bd.../
   │      └── report.docx
   │
   └── f17a.../
          └── image.png
```

Пользователь не должен получать прямой публичный URL до файла.

Правильная схема:

```text
User
 ↓
GET /documents/123/download
 ↓
Backend
 ↓
Проверка прав
 ↓
File Storage
 ↓
Файл
```

Таким образом, сначала Backend проверяет:

```text
Имеет ли пользователь доступ?
```

И только после этого отдает файл.

# 7. Integrity / Hash Module

Модуль отвечает за вычисление и проверку BLAKE2b-256.

Например:

```text
BLAKE2b(file) 
      ↓
b33a2ac7...
```

Он используется в двух основных процессах.

### Регистрация

```text
Файл
 ↓
BLAKE2b-256
 ↓
Hash
 ↓
Blockchain
```

### Проверка

```text
Проверяемый файл
       ↓
     BLAKE2b-256
       ↓
Current Hash
       │
       ▼
Registered Hash
       │
       ▼
    Сравнение
     /     \
  equal   different
    ↓        ↓
 VALID    INVALID
```

---

# 8. Blockchain Module

Этот модуль изолирует Backend от конкретной blockchain-сети.

То есть Document Module не должен сам создавать blockchain-транзакции.

Он вызывает:

```text
BlockchainService.registerDocument(...)
```

Например:

```text
registerDocument(
    documentId,
    hash
)
```

Blockchain Module:

1. формирует транзакцию;
2. подписывает ее;
3. отправляет в blockchain;
4. получает transaction hash;
5. отслеживает подтверждение;
6. обновляет статус документа.

Состояния могут быть:

```text
HASH_CALCULATED
       ↓
PENDING
       ↓
SENT
       ↓
CONFIRMING
       ↓
CONFIRMED
```

При ошибке:

```text
FAILED
```

Требования предусматривают, что ошибка blockchain не должна приводить к потере уже загруженного документа, а неудачную регистрацию можно повторить.

---

# 9. Smart Contract

Если используется blockchain со smart contracts, можно сделать очень простой контракт.

Условно:

```text
registerDocument(
    documentId,
    documentHash
)
```

Blockchain хранит:

```text
DocumentProof
------------------------
document_id
document_hash
timestamp
```

Важно:

```text
FILE НЕ ПОПАДАЕТ В BLOCKCHAIN
```

В blockchain записывается только:

```text
HASH + идентификатор + время
```

Это соответствует модели системы: само содержимое документа не должно публиковаться в blockchain.

# 10. Access Module

Отвечает за передачу документов между пользователями.

Например:

```text
POST /documents/{id}/share
```

Запрос:

```json
{
    "receiverId": "user-2"
}
```

Создается запись:

```text
DocumentPermission

document_id = 123
user_id = user-2
permission = READ
```

После этого:

```text
user-1

Мои документы
     │
     │ Передать
     ▼

document 123

     │
     ▼

user-2

Входящие документы
```

Модуль должен контролировать права на просмотр, скачивание, передачу и проверку документа — именно такие операции указаны в требованиях.

# 18. Решения по архитектуре (v2)

Этот раздел дополняет схему выше и фиксирует, что мы делаем в MVP. Если он расходится с разделами 1–17, правильным считается он.

## 18.1. Хеш-функция: BLAKE2b-256

- Алгоритм: **BLAKE2b** (RFC 7693), длина дайджеста **32 байта (256 бит)**, без ключа.
- Почему BLAKE2b, а не SHA-256: такая же криптостойкость и быстрее на 64-битных CPU, что заметно на больших файлах.
- Формат хранения: строка **hex в нижнем регистре, 64 символа**, например `a83f...91bc`. Одинаково в БД, API и блокчейне.
- Файл хешируется **потоково** (кусками по 64 КБ), целиком в память не читается.
- Хеш считается **по байтам файла**. Имя, дата и владелец в хеш не входят: у одинакового содержимого одинаковый хеш.
- Пароли хешируются **не BLAKE2**, а **Argon2id** (NFR-1). BLAKE2 — быстрая функция, для паролей это минус.
- Важно для текстов и презентаций: BLAKE2 — это **хеширование, а не шифрование**. Файл им нельзя расшифровать, можно только сравнить отпечатки. Если позже понадобится шифровать файлы в хранилище (NFR-12), это отдельный алгоритм, например AES-256-GCM.

Библиотеки: Python — `hashlib.blake2b(digest_size=32)`; .NET — NuGet `Blake2Fast` или `Konscious.Security.Cryptography.Blake2`; JS — `blakejs`.

Контрольный пример для тестов: BLAKE2b-256 от пустой строки = `0e5751c026e543b2e8ab2eb06099daa1d1e5df47778f7787faab45cdf12fe3a8`.

## 18.2. Блокчейн: собственный учебный реестр

В MVP вместо внешней сети со смарт-контрактом пишем **свой блокчейн** внутри Blockchain Module (спринт 2: классы записи, блока и цепочки). Модуль закрыт интерфейсом, поэтому позже его можно заменить на Ethereum или другую сеть, не трогая остальной код.

```text
IBlockchainService
├── RegisterDocument(documentId, fileHash) → RegistrationResult (txId, blockIndex, status)
└── ValidateChain()                        → bool
```

`GetProof(fileHash)` (поиск записи по хешу файла) в спринт 2 не входит, добавим позже вместе с проверкой целостности по blockchain.

Структура:

```text
Record (запись = «транзакция»)          Block
─────────────────────────────           ─────────────────────────────
record_id    UUID                       index          int (0 = genesis)
document_id  UUID                       timestamp      UTC, unix ms
file_hash    hex(BLAKE2b-256)           prev_hash      hex(BLAKE2b-256)
timestamp    UTC, unix ms               records[]      Record
record_hash  BLAKE2b(канон. JSON)       hash           BLAKE2b(заголовок блока)
```

Правила:

- В записи **нет** имени файла, email и содержимого, только хеш и идентификаторы (NFR-2).
- `record_hash` = BLAKE2b-256 от канонического JSON полей записи без самого `record_hash`.
- `hash` блока = BLAKE2b-256 от канонического JSON заголовка (`index, timestamp, prev_hash, record_hashes`), где `record_hashes` это хеши всех записей блока по порядку. Merkle root и nonce в MVP нет.
- Первый блок (genesis) создаётся вручную с фиксированными полями: `index` 0, `timestamp` 0, `prev_hash` из 64 нулей, записей нет. Поэтому его хеш всегда одинаковый.
- Цепочка валидна, если первый блок это genesis, `index` каждого блока равен его позиции, у каждого блока `prev_hash` равен `hash` предыдущего, а пересчитанные хеши блока и всех его записей совпадают с сохранёнными.
- Proof-of-Work в MVP нет: блок формируется сразу при регистрации документа (`AddBlock` с одной записью), поэтому регистрация возвращает `CONFIRMED` или `FAILED`. Статус `PENDING` оставлен для будущей схемы, где записи копятся в пуле и упаковываются в блок по таймеру.
- Цепочка хранится в JSON-файле `chain.json` (интерфейс `IChainRepository`, реализация `JsonChainRepository`). Запись идёт через временный файл с подменой. Позже хранилище можно заменить на PostgreSQL (таблицы `blocks`, `block_records`), не трогая ядро.
- При создании `Blockchain` цепочка загружается и выполняется `ValidateChain()`. Если файл нечитаем или цепочка битая, добавление блоков блокируется, ошибка уходит в лог, файл не перезаписывается. Если файла нет, создаётся genesis.
- `transaction_hash` документа = `record_hash`. Номер блока сохраняется в `blockchain_tx.block_number`.

## 18.3. Соглашение о формате данных

- Кодировка UTF-8, JSON в `camelCase`.
- Время в UTC: в API ISO 8601 (`2026-09-24T12:30:00Z`), в блокчейне unix ms.
- Идентификаторы: UUID v4 строкой.
- Хеши: hex в нижнем регистре, без префикса `0x`.
- Канонический JSON для хеширования: ключи отсортированы, без пробелов, числа без экспоненты.
- Ошибки API в формате RFC 7807 (`application/problem+json`): `type, title, status, detail, traceId`.
- Статусы документа: `UPLOADED → HASH_CALCULATED → PENDING → CONFIRMED` и отдельно `FAILED`, их можно повторить (NFR-6).
