# Git: ветки, коммиты, процесс

## Базовые правила

1. Ветки (Без базара)

* `main` — Святая святых. Тут только то, что в проде. Никаких коммитов напрямую.
* `develop` — Тусовка фич. Всё, что должно уйти в прод, сначала сюда.
* `feature/что-делаем` — Новая тема. Ветвим от `develop`.
* `bugfix/что-чиним` — Правим косяки. Тоже от `develop`.
* `fixfuck/шо-то-нахуй` — Прод горит, всё срочно, по коням! Ветвим от `main`, чиним, льем обратно в `main` и в `develop` (синхронизируем).

2. Git-Этикет (Чё как)

* В `main` и `develop` не пушим. Только через MR (Merge Request). Защиту веток в репе настрой, чтоб ни-ни.
* Прежде чем делать новую ветку — обнови `develop`:


```bash
    git checkout develop && git pull

```

* Коммиты пишем по-человечески
   * Пример: `feat(auth): добавил капчу
   * Пример: `fixfuck(cart): починил баг с ценами

3. CI/CD (В будущем пока похуй)
Сам запускается на каждый пуш.

* Линтер: Чтоб код не выглядел как кал.
* Сборка: Чтоб проект вообще компилился.
* Юнит-тесты: Быстрые. Упали — мерж запрещен.
* Интеграционные тесты: Гоняются на тестовом стенде с тестовыми данными (отдельная база!). Только если они зелены, можно думать о мерже в `develop`.

4. Окружение (Где живет код)

* Песочница (Test/Dev): Сюда улетает каждая ветка при создании MR. Там она живет, гоняются интеграционные тесты. Данные — тестовые (фикстуры), накатываются перед каждым тестом.
* PreProd: Ветка `develop`. Выкатывается автоматом после каждого вмержа. Максимально похоже на прод. Тут курим дым.
* Prod: Ветка `main`.

5. Таск-менеджер (Статусы задач)
Берем любой (Jira, Trello, YouTrack, доска в туалете). Главное — статусы:

1. Новое (TODO): Задача есть.
2. В работе (In Progress): создал ветку, делаешь
3. !!!ПОТОМ На тестировании (Testing): MR прошел ревью. CI/CD гоняет тесты на стенде. Если тесты упали — задача летит обратно в В работе.
4. Готово (Done): Тесты зелены, MR вмержен в `develop`. Задача закрыта счастливо.

Коротко: Жизненный цикл задачи

1. Задачу взял
2. Создал ветку `feature/kill-null-pointer` от `develop`.
3. Написал код написал тесты функциональные, запушил, создал MR в `develop`.
4. CI/CD выкатил твою ветку на тестовый стенд, прогнал тесты.
5. Тесты зелены -> заебись. Нет - обратно в работу
6. Если всё ок, апрув на прод и мерж в `main`.

## Дополнительные правила

### 6. Как называть ветки, чтобы всё было понятно без вопросов

Формат: `тип/SER-номер-коротко-что-делаем`

* `SER-12` — номер задачи из YouGile. Тогда по ветке сразу видно, какая это задача, а YouGile и CI могут связать их между собой.
* Только латиница, нижний регистр, слова через дефис. Без пробелов, кириллицы, `_` и заглавных букв.
* Коротко, 3–5 слов. `feature/SER-12-upload-file`, а не `feature/SER-12-sdelal-zagruzku-faila-i-eshe-chut-chut`.
* Одна ветка — одна задача. Если захотелось «заодно поправить», это отдельная задача и отдельная ветка.

| Тип | От чего ветвим | Куда мержим | Пример |
|---|---|---|---|
| `feature/` | `develop` | `develop` | `feature/SER-12-upload-file` |
| `bugfix/` | `develop` | `develop` | `bugfix/SER-31-wrong-hash-on-empty-file` |
| `fixfuck/` | `main` | `main` + `develop` | `fixfuck/SER-40-chain-validation-crash` |
| `refactor/` | `develop` | `develop` | `refactor/SER-18-split-document-service` |
| `docs/` | `develop` | `develop` | `docs/SER-5-architecture-v2` |
| `test/` | `develop` | `develop` | `test/SER-22-blockchain-unit-tests` |
| `ci/` | `develop` | `develop` | `ci/SER-8-docker-compose` |
| `chore/` | `develop` | `develop` | `chore/SER-9-update-deps` |
| `release/` | `develop` | `main` + `develop` | `release/0.1.0` |

Префиксы нужны не только людям: если позже подключим CI (Gitea Actions, см. `05-ci-cd.md`), он будет выбирать шаги по типу ветки.

### 7. Коммиты (Conventional Commits)

Формат: `тип(модуль): что сделал` + номер задачи в конце.

```text
feat(documents): загрузка файла с потоковым BLAKE2b SER-12
fix(integrity): пустой файл давал неверный хеш SER-31
fixfuck(blockchain): падение ValidateChain на genesis-блоке SER-40
refactor(access): вынес проверку прав в AccessService SER-18
test(blockchain): тесты на подмену блока SER-22
docs(architecture): раздел про формат данных SER-5
build: docker-compose для локального запуска SER-8
chore(deps): обновил SQLAlchemy SER-9
```

* Типы: `feat`, `fix`, `fixfuck`, `refactor`, `test`, `docs`, `ci`, `build`, `chore`.
* Модули совпадают с архитектурой: `auth`, `documents`, `access`, `integrity`, `blockchain`, `audit`, `storage`, `frontend`, `infra`.
* Пишем, **что** сделано, в прошедшем времени. `фикс`, `правки`, `asdasd`, `wip` не принимаются.
* Один коммит — одно логическое изменение. Сломал сборку в коммите — чини в следующем, не копи.

### 8. Merge Request

У нас GitHub, поэтому MR там называется **Pull Request (PR)**. Правила те же.

* Название = главный коммит: `feat(documents): загрузка файла SER-12`.
* В описании: что сделано, как проверить, ссылка на задачу YouGile, скриншот, если менялся UI.
* Размер: до ~400 строк изменений. Если больше, дели.
* Ревью: минимум **1 апрув не от автора** (кто обязателен, см. `03-team-roles.md`).
* Мерж в `develop` через **Squash and merge**: в `develop` одна фича = один коммит.
* Мерж в `main` через **Merge commit** из `release/*` или `fixfuck/*`. Плюс тег версии.
* Ветку после мержа удаляем.
* CI у нас нет, поэтому автор перед PR сам прогоняет сборку и тесты, а ревьюер подтверждает, что проверил у себя.
* Перед мержем ветку обновляем от `develop` через `git pull --rebase origin develop`, конфликты решает автор ветки.
* Ревьюер отвечает в течение суток. Если не успевает, пишет в чат, а не молчит.

### 9. Чего в git быть не должно

* Секретов: `.env`, ключей, паролей, токенов, приватных ключей блокчейна. Всё это только в `.env` локально (и в секретах CI, если он появится). Если секрет засветился в коммите, **меняем секрет**, переписывать историю мало.
* Файлов пользователей, дампов БД, логов, `__pycache__/`, `.venv/`, `node_modules/`, сборок.
* Больших бинарников. Картинки для документации — в `docs/img/`, до 1 МБ.

### 10. Версии и релизы

* SemVer: `MAJOR.MINOR.PATCH`. До первой сдачи живём в `0.x.y`.
* В конце спринта: `release/0.N.0` от `develop` → PR в `main` → тег `v0.N.0` → мерж обратно в `develop`.
* Fixfuck поднимает PATCH: `v0.2.1`.
* `CHANGELOG.md` обновляется в релизной ветке по заголовкам PR.

### 11. Связка с YouGile

Колонки доски «Канбан» и когда туда попадает задача:

| Колонка | Когда |
|---|---|
| БЭКЛОГ | идея или задача без спринта |
| Новые задачи | задача взята в текущий спринт, ещё не начата |
| В работе | создана ветка `feature/SER-12-...` |
| Тестирование | открыт PR, тесты локально зелёные, идёт ревью |
| Доработка | тесты упали или ревью вернуло замечания |
| Завершенные | PR вмержен в `develop` |

Статусы двигает автор задачи. Если забыл, это может сделать Claude через `yougile/yg.py`.

### 12. Защита веток

* Для `main` и `develop`: без прямого пуша и force-push, только PR с минимум 1 апрувом, для `main` апрув Lead.
* На бесплатном GitHub в приватном репозитории правила защиты не применяются, поэтому у нас это **договорённость команды**. Нарушил — откатываем и разбираем на созвоне.
* Если понадобится техническая защита и CI, переезжаем на **Gitea**: там protected branches и обязательные проверки есть бесплатно (см. `05-ci-cd.md`).
