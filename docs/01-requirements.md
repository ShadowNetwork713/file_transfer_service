# Сервис безопасной передачи файлов с подтверждением целостности на основе blockchain

## 1. Описание системы

Разрабатываемая система представляет собой сервис безопасной загрузки, передачи и проверки файлов и документов с использованием технологии blockchain для подтверждения их целостности и факта существования в определенный момент времени.

Основная идея сервиса заключается в следующем:

**Пользователь → загружает файл → система вычисляет хеш файла → хеш регистрируется в blockchain → файл передается или хранится → впоследствии целостность файла может быть проверена.**

Например, пользователь загружает документ `contract.pdf`.

Для файла вычисляется криптографический хеш:

`BLAKE2b-256(contract.pdf) = A83F...91BC`

Полученное значение записывается в blockchain вместе с необходимой служебной информацией.

Если файл впоследствии изменится хотя бы на один байт, его хеш станет другим. Следовательно, система сможет определить, что файл отличается от первоначально зарегистрированной версии.

При этом сам документ не требуется хранить в blockchain. В blockchain сохраняется только его хеш и информация о регистрации. Это позволяет не раскрывать содержимое документа и значительно уменьшает объем данных, записываемых в blockchain.

---

# 2. Цель системы

Основная цель системы — предоставить пользователям возможность безопасно передавать документы и независимо подтверждать:

* целостность файла;
* отсутствие изменений после регистрации;
* факт существования файла на определенный момент времени;
* принадлежность зарегистрированного файла определенной записи в системе;
* историю операций с документом.

Сервис может использоваться, например, для передачи договоров, актов, отчетов, юридических документов, результатов исследований, исходного кода и других файлов, для которых важно доказать неизменность содержимого.

---

# 3. Роли пользователей

В системе можно выделить следующие основные роли.

### Пользователь-отправитель

Может:

* зарегистрироваться и авторизоваться;
* загружать документы;
* регистрировать хеш документа в blockchain;
* отправлять документ другому пользователю;
* просматривать статус документа;
* проверять его целостность;
* видеть историю операций.

### Пользователь-получатель

Может:

* получать документы;
* скачивать переданные ему файлы;
* проверять их целостность;
* просматривать информацию о blockchain-регистрации;
* подтверждать получение документа.

### Администратор

Может:

* управлять пользователями;
* блокировать учетные записи;
* просматривать технический журнал операций;
* контролировать работоспособность системы;
* просматривать состояние blockchain-транзакций;
* управлять системными настройками.

# 4. Функциональные требования

## FR-1. Регистрация пользователя

Система должна предоставлять возможность создания учетной записи.

Пользователь должен иметь возможность указать:

* email;
* пароль;
* имя.

Система должна проверять уникальность email и корректность введенных данных.

---

## FR-2. Авторизация

Система должна позволять зарегистрированному пользователю войти в систему.

После успешной авторизации пользователь должен получить доступ к своим документам и операциям.

---

## FR-3. Загрузка файла

Система должна позволять пользователю загружать файл.

При загрузке система должна:

1. принять файл;
2. проверить допустимый размер;
3. проверить допустимый формат;
4. сохранить файл;
5. вычислить его криптографический хеш.

Используется алгоритм BLAKE2b с длиной дайджеста 256 бит (BLAKE2b-256), подробнее в `02-architecture.md`, раздел «Решения».

---

## FR-4. Вычисление хеша

После загрузки файла система должна автоматически вычислить его хеш.

Хеш должен однозначно соответствовать содержимому файла.

Даже минимальное изменение содержимого должно приводить к изменению хеша.

---

## FR-5. Регистрация хеша в blockchain

Система должна иметь возможность отправить хеш файла в blockchain.

Blockchain-запись должна содержать как минимум:

* хеш файла;
* идентификатор документа;
* дату/время регистрации.

После успешной регистрации система должна сохранить идентификатор blockchain-транзакции.

Например:

`Document ID: 152`

`Hash: A83F...91BC`

`Blockchain transaction: 0x45a...92f`

`Registered at: 24.09.2026 12:30`

**Уточнение для MVP (спринт 2, собственный блокчейн).** Запись (`Record`) содержит `recordId`, `documentId`, `fileHash`, `timestamp` (UTC, unix ms) и `recordHash`. Идентификатором blockchain-транзакции (`transaction_hash`) служит `recordHash`. Дополнительно сохраняется номер блока (`blockchain_tx.block_number`). Имя файла и персональные данные в запись не попадают (NFR-2).

---

## FR-6. Получение статуса blockchain-транзакции

Система должна отображать статус регистрации документа.

Возможные состояния:

**Вычисление хеша → Отправлено в blockchain → Ожидание подтверждения → Подтверждено**

Также должен быть предусмотрен статус ошибки регистрации.

**Уточнение для MVP (спринт 2).**

* «Подтверждено» (`CONFIRMED`) означает, что запись попала в блок при `AddBlock`, блок сохранён в `chain.json`, а цепочка прошла проверку. Блок формируется сразу при регистрации документа, без пула и ожидания по таймеру.
* Поэтому в MVP пользователь видит два итоговых статуса: «Подтверждено» и «Ошибка регистрации» (`FAILED`). Промежуточные «Отправлено» и «Ожидание подтверждения» (`PENDING`) заведены в модели, но сейчас не возвращаются, они понадобятся при переходе на асинхронное формирование блоков или внешнюю сеть.
* `FAILED` возникает при повреждённой цепочке или ошибке записи на диск. Документ при этом не теряется, регистрацию можно повторить (NFR-6). Повтор уже зарегистрированного документа с тем же хешем возвращает прежний результат и новый блок не создаёт.
* Пользователю показываем текст вида «Целостность документа зарегистрирована и подтверждена» без технических деталей (NFR-9). Номер блока и `recordHash` доступны отдельно.

---

## FR-7. Проверка целостности файла

Система должна позволять пользователю проверить файл.

Пользователь загружает файл для проверки.

Система:

1. вычисляет его текущий хеш;
2. получает зарегистрированный хеш;
3. сравнивает значения.

Если значения совпадают:

**Файл является оригинальным и не был изменен после регистрации.**

Если значения различаются:

**Целостность файла не подтверждена. Файл отличается от зарегистрированной версии.**

**Уточнение для MVP (спринт 2).** Зарегистрированный хеш берётся из записи документа (`hash_blake2b`), а надёжность самой записи подтверждает проверка цепочки `ValidateChain()`. Результат `VALID` выдаётся, только если хеши равны и цепочка валидна. Если цепочка повреждена, результат `INVALID` с пометкой о проблеме цепочки. Поиск записи в блокчейне по хешу файла (`GetProof`) в спринт 2 не входит.

---

## FR-8. Передача документа

Пользователь должен иметь возможность передать документ другому зарегистрированному пользователю.

Для передачи пользователь выбирает документ и получателя.

Получатель должен увидеть документ в разделе входящих документов.

---

## FR-9. Управление доступом

Документ не должен быть доступен пользователям, которым владелец не предоставил доступ.

Система должна контролировать права на:

* просмотр;
* скачивание;
* передачу;
* проверку документа.

---

## FR-10. Скачивание файла

Получатель с соответствующими правами должен иметь возможность скачать файл.

Система должна обеспечивать скачивание именно той версии файла, которая соответствует зарегистрированному хешу.

---

## FR-11. История документа

Система должна вести историю операций.

Например:

`12:01 — файл загружен`

`12:01 — BLAKE2b-256 вычислен`

`12:02 — хеш отправлен в blockchain`

`12:04 — транзакция подтверждена`

`12:10 — доступ предоставлен user2@example.com`

`12:15 — файл скачан получателем`

---

## FR-12. Просмотр документов

Пользователь должен иметь возможность просматривать список:

* своих документов;
* полученных документов;
* отправленных документов.

Для каждого документа должны отображаться:

* название;
* размер;
* владелец;
* дата загрузки;
* статус;
* статус blockchain-регистрации.

---

## FR-13. Поиск документов

Система должна позволять выполнять поиск документов, например, по:

* названию;
* идентификатору;
* владельцу;
* дате;
* хешу.

---

## FR-14. Удаление документа

Пользователь должен иметь возможность удалить файл из файлового хранилища, если это разрешено правилами системы.

При этом запись о хеше в blockchain удалить нельзя.

Таким образом, сохраняется доказательство того, что определенный файл ранее существовал.

---

## FR-15. Проверка документа без авторизации

В качестве дополнительной функции можно предоставить публичную страницу проверки.

Пользователь вводит:

* файл;

или

* его хеш.

Система сообщает, существует ли такой хеш в blockchain.

При этом приватная информация о владельце документа не должна раскрываться.

---

## FR-16. Аудит действий

Система должна вести журнал значимых действий:

* вход в систему;
* загрузка документа;
* регистрация документа;
* передача;
* скачивание;
* проверка;
* удаление;
* изменение прав доступа.

---

# 5. Нефункциональные требования

## NFR-1. Безопасность

Передача данных между клиентом и сервером должна происходить по защищенному соединению HTTPS.

Пароли пользователей должны храниться только в виде криптографических хешей.

Необходимо использовать надежный алгоритм хеширования паролей, например Argon2 или bcrypt.

---

## NFR-2. Конфиденциальность

Содержание документов не должно записываться в публичный blockchain.

В blockchain должен передаваться только хеш документа и минимально необходимая информация.

---

## NFR-3. Целостность

Система должна использовать криптографически стойкий алгоритм вычисления хеша, BLAKE2b-256.

Система не должна позволять незаметно заменить файл после регистрации его хеша.

---

## NFR-4. Производительность

Вычисление хеша обычного документа должно выполняться за приемлемое для пользователя время.

Для файлов небольшого размера получение хеша должно занимать, как правило, не более нескольких секунд.

Операции blockchain могут выполняться дольше, поэтому интерфейс не должен блокироваться во время ожидания подтверждения транзакции.

---

## NFR-5. Масштабируемость

Архитектура должна обеспечивать возможность увеличения:

* числа пользователей;
* количества документов;
* количества одновременно выполняемых проверок;
* количества blockchain-транзакций.

---

## NFR-6. Надежность

Ошибка blockchain-сети не должна приводить к потере загруженного пользователем документа.

Если регистрация не удалась, система должна сохранить соответствующий статус и позволить повторить операцию.

---

## NFR-7. Доступность

Сервис должен быть доступен пользователям большую часть времени.

Целевой показатель доступности, например:

**99,5 % времени в месяц.**

---

## NFR-8. Совместимость

Веб-интерфейс должен корректно работать в актуальных версиях основных браузеров:

* Google Chrome;
* Mozilla Firefox;
* Microsoft Edge;
* Safari.

---

## NFR-9. Удобство использования

Пользователь должен иметь возможность выполнить основные операции без знания технологии blockchain.

Например, вместо технического сообщения:

`Transaction 0x71... confirmed in block 128472`

пользователь должен видеть:

**Целостность документа зарегистрирована и подтверждена.**

При необходимости техническую информацию можно открыть отдельно.

---

## NFR-10. Восстановление после ошибок

В случае временной недоступности blockchain система должна повторить отправку транзакции либо предоставить пользователю возможность повторного запуска.

---

## NFR-11. Логирование

Критические ошибки и системные события должны записываться в журнал.

Логи должны позволять определить:

* время ошибки;
* пользователя;
* операцию;
* причину ошибки.

---

## NFR-12. Защита файлового хранилища

Файлы должны храниться в защищенном хранилище.

Доступ напрямую по адресу файла без проверки прав пользователя не должен быть возможен.

В более защищенном варианте документы могут храниться в зашифрованном виде.

---

# 6. User Stories

## US-1. Загрузка документа

**Как пользователь,
я хочу загрузить документ в систему,
чтобы зарегистрировать его исходное состояние.**

### Критерии приемки

* пользователь может выбрать файл;
* файл успешно загружается;
* система вычисляет BLAKE2b-256;
* пользователю отображается информация о документе.

---

## US-2. Регистрация документа

**Как пользователь,
я хочу зарегистрировать хеш моего документа в blockchain,
чтобы позднее можно было доказать, что такой документ существовал.**

Критерии приемки:

* хеш передается в blockchain;
* система получает идентификатор транзакции;
* после подтверждения отображается статус «Подтверждено».

---

## US-3. Проверка документа

**Как пользователь,
я хочу загрузить документ для проверки,
чтобы узнать, соответствует ли он ранее зарегистрированной версии.**

Критерии приемки:

* система вычисляет новый хеш;
* новый хеш сравнивается с зарегистрированным;
* система показывает результат проверки.

---

## US-4. Передача документа

**Как владелец документа,
я хочу отправить его другому пользователю,
чтобы безопасно передать ему подтвержденную версию файла.**

---

## US-5. Получение документа

**Как получатель,
я хочу увидеть переданный мне документ,
чтобы скачать его и проверить его подлинность.**

---

## US-6. Просмотр истории

**Как владелец документа,
я хочу видеть историю операций с документом,
чтобы понимать, когда он был загружен, зарегистрирован и передан.**

---

## US-7. Проверка даты существования

**Как пользователь,
я хочу увидеть дату blockchain-регистрации документа,
чтобы подтвердить существование данной версии документа не позднее указанного времени.**

Здесь корректнее говорить именно о подтверждении существования файла **не позднее момента регистрации blockchain-транзакции**.

Blockchain сам по себе не доказывает, кто физически создал файл или являлся его автором.

---

# 7. Use Cases

## UC-1. Загрузка и регистрация документа

**Актор:** пользователь.

**Предусловия:** пользователь авторизован.

### Основной сценарий

1. Пользователь нажимает «Загрузить документ».
2. Выбирает файл.
3. Клиент передает файл серверу.
4. Сервер проверяет файл.
5. Система сохраняет документ.
6. Система вычисляет BLAKE2b-256.
7. Система создает запись документа в БД.
8. Хеш передается blockchain-модулю.
9. Формируется blockchain-транзакция.
10. Транзакция отправляется в blockchain.
11. Blockchain подтверждает транзакцию.
12. Система сохраняет transaction ID.
13. Пользователь видит статус «Подтверждено».

### Альтернативный сценарий

Если blockchain временно недоступен:

1. документ сохраняется;
2. его хеш вычисляется;
3. статус устанавливается в «Ожидает регистрации»;
4. после восстановления соединения выполняется повторная регистрация.

---

## UC-2. Проверка целостности документа

**Актор:** пользователь.

**Предусловия:** существует зарегистрированный документ.

### Основной сценарий

1. Пользователь выбирает «Проверить документ».
2. Загружает файл.
3. Система вычисляет BLAKE2b-256 файла.
4. Система получает blockchain-запись.
5. Хеши сравниваются.
6. Они совпадают.
7. Пользователь получает сообщение:

**«Целостность документа подтверждена».**

### Альтернативный сценарий

Если хеши не совпадают:

**«Целостность документа не подтверждена. Содержимое файла было изменено либо это другой файл».**

---

## UC-3. Передача документа

**Актор:** отправитель.

### Сценарий

1. Пользователь открывает документ.
2. Нажимает «Передать».
3. Выбирает получателя.
4. Система проверяет наличие пользователя.
5. Система предоставляет получателю право доступа.
6. Получателю приходит уведомление.
7. Документ появляется во входящих документах получателя.

---

## UC-4. Получение документа

**Актор:** получатель.

1. Получатель открывает список входящих документов.
2. Выбирает документ.
3. Видит информацию о его регистрации.
4. Проверяет blockchain-статус.
5. Скачивает документ.
6. При необходимости запускает дополнительную проверку целостности.

---

# 9. Бизнес-процесс регистрации документа

Отдельно процесс регистрации можно описать следующим образом:

**Загрузка файла → вычисление хеша → сохранение информации о документе → создание blockchain-транзакции → отправка транзакции → подтверждение blockchain → сохранение номера транзакции и номера блока → документ получает статус «Зарегистрирован».**

# 10. Бизнес-процесс проверки

Процесс проверки состоит из следующих этапов:

**Получение проверяемого файла → вычисление BLAKE2b-256 → получение зарегистрированного хеша → сравнение → формирование результата.**

Условие:

`HashUploadedFile == HashBlockchain`

Если условие выполняется:

**Integrity = VALID**

Если не выполняется:

**Integrity = INVALID**

# 12. Что именно доказывает система

Очень важно правильно сформулировать это в работе.

Blockchain не доказывает автоматически, что документ является юридически подлинным или что его создал конкретный человек.

Система позволяет доказать следующее:

**на момент регистрации существовал файл, обладающий конкретным криптографическим хешем.**

Если предоставленный позднее файл имеет такой же BLAKE2b-256, можно с крайне высокой степенью уверенности утверждать, что его содержимое совпадает с содержимым зарегистрированного файла.

Таким образом обеспечивается механизм подтверждения **целостности и существования документа на определенный момент времени**.

Для подтверждения непосредственно личности автора дополнительно может использоваться электронная цифровая подпись.

# 13. Расширенный вариант системы

В дальнейшем систему можно расширить следующими возможностями:

* электронная цифровая подпись документов;
* версии документов;
* QR-код для проверки документа;
* публичная страница проверки;
* API для сторонних систем;
* уведомления о получении документа;
* шифрование документов;
* одноразовые ссылки;
* ссылки с ограниченным сроком действия;
* подтверждение получения документа;
* хранение нескольких версий одного документа;
* интеграция с корпоративными информационными системами.

В этом случае можно реализовать полный процесс:

**Создание документа → подписание → хеширование → blockchain-регистрация → безопасная передача → получение → проверка подписи → проверка blockchain → подтверждение получения.**
